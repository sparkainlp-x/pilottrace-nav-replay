# PilotTrace Navigation Replay Pack

A deterministic, **fully SYNTHETIC** software replay of GNSS-denied maritime navigation. Navigation residuals are mapped explicitly into OES-32 blocks and OES-512 (16 × 32) frames, then scored and evidenced through the existing, unmodified [`sparkainlp-x/pilottrace`](https://github.com/sparkainlp-x/pilottrace) package. Every run writes a hash-chained provenance manifest and an evidence report.

## Boundaries

Read these first.

- **The data is synthetic only.** The route, vessel motion, GNSS, gyro, speed log, compass, faults and labels are all generated by this software from seed 42. No real recording, chart, vessel, receiver or jammer is involved.
- **No physical sensor or other hardware is involved.** The `hypothetical_low_drift` inertial profile used in one comparison table is a *parameter assumption* and does not model any device.
- **No sensor benefit, calibration or fitness for operational use is established.**
- **This is a deterministic software replay only.** It is not a navigation system, an integrity monitor, an alarm, a safety function or a certified product. It makes no readiness, medical or consciousness claims.
- Every number in this repository is tagged **SYNTHETIC**. Performance on real data is **UNRUN**. No number is **REPORTED** (measured on named real data).

## What it does

```text
scenarios (seed 42) ──> sensors + simple estimator ──> 16 residual channels per epoch
      └─> oes_adapter: 32-epoch window per channel = one 32-value block; 16 blocks = 512-value frame
            ├─> pilottrace.analyze_bytes (unmodified, pinned, hash-checked)  ← scoring of record
            └─> fail-closed reference scoring (must agree on every latch decision)
                  └─> evidence_report.{json,md} + provenance_manifest.json (SHA-256 of everything)
```

### Scenarios

The scenarios are in `pilottrace_nav/scenarios/`. Each is a 900 s route at 1 Hz with labelled degradation events:

| scenario | labelled event (SYNTHETIC parameters) |
|---|---|
| `nominal` | none |
| `total_dropout` | no GNSS fix, epochs 300–600 |
| `jamming` | epochs 300–480: C/N0 −18 dB-Hz, 3–5 satellites lost, position noise σ 12 m, velocity noise σ 0.6 m/s, 25% of fixes lost |
| `spoof_ramp` | epochs 300–600: a consistent spoofer drags position east at 0.5 m/s, with matching velocity |
| `spoof_step` | epochs 400–550: GNSS position offset by 120 m north |
| `inertial_drift` | from epoch 300 to the end: gyro bias +0.03 deg/s |
| `sensor_dropouts` | gyro missing 250–270, speed log missing 450–490, compass missing 650–680 |

The estimator is deliberately simple and documented in `scenarios/simulate.py`:

- heading is the gyro rate integrated freely;
- speed comes from the speed log;
- position is dead-reckoned, then updated with a constant-gain GNSS step behind a 30 m innovation gate;
- after 10 consecutive rejected fixes, the estimate is re-initialised to the next fix.

Each sensor draws its noise from its own seeded stream, so all scenarios share identical noise outside their events.

### OES adapter: the explicit mapping

The adapter is `pilottrace_nav/integrations/oes_adapter.py`.

- **Channels.** Each of the 16 channels is a navigation residual divided by a declared scale, so |value| = 1 means one declared tolerance:
  - 0–1: GNSS position innovation, east and north (20 m);
  - 2–3: GNSS velocity innovation, east and north (1.2 m/s);
  - 4: C/N0 deficit (30 dB-Hz);
  - 5: satellite deficit (10);
  - 6: GNSS-unavailable flag;
  - 7: gate-rejected flag;
  - 8: gyro heading minus compass (15°);
  - 9: speed log minus GNSS speed (1.5 m/s);
  - 10–12: gyro, speed-log and compass unavailable flags;
  - 13–15: reserved, always 0.
- **Frame layout.** Block *b* of the frame for epoch *t* is channel *b* over epochs *t*−31 … *t*, oldest first: `frame[32b + j] = r[t−31+j][b]`. Frames start at epoch 31; there is no padding and no imputation.
- **Classical residual.** `R = max|x − x_ref|`, with `x_ref = 0`.
- **Latch.** `S = 0.45·Peak + 0.35·RMS + 0.20·MeanAbs ≥ τ`, with τ = 0.50 by default. A frame latches when any block latches.
- **Fail-closed.** NaN, ±inf, booleans, non-numbers, oversized integers and any wrong shape raise `FailClosedError`; nothing is clipped or imputed. A missing measurement is handled explicitly upstream: its residual is set to 0.0 *and* its availability flag to 1.0. A single 1.0 in a 32-epoch window scores 0.518 ≥ 0.50, so a missing sensor always latches and never passes silently.
- **Cross-check.** Every frame is scored by pilottrace and by the adapter. The two agree on every latch decision (largest score difference 8.9·10⁻¹⁶); any disagreement aborts the run.
- **Frame labels.** A frame is labelled degraded when any epoch in its window is degraded.

### Provenance

`provenance/manifest.py` writes `provenance_manifest.json`, which records:

- the seed and the config with its SHA-256;
- the SHA-256 of the scenario catalogue;
- the code version and the SHA-256 of every package source file (plus a tree hash);
- the pinned pilottrace commit and the SHA-256 of its source files;
- the SHA-256 and size of every output.

It contains no timestamps or host data, so it is byte-identical across runs. `pilottrace-nav-replay verify <manifest>` re-hashes everything and exits with code 4 on any mismatch. `provenance/evidence_report.py` writes the JSON and Markdown evidence report.

## Results of the committed replay (all SYNTHETIC)

`examples/output/evidence_report.md` is regenerated in CI and compared byte for byte. It covers 869 frames per scenario at τ = 0.50.

| scenario | latched during event? | latency | false-alarm frames | max nav error |
|---|---|---|---|---|
| nominal | n/a (no event) | n/a | 0 of 869 | 2.7 m |
| total_dropout | yes | 0 s | 4 (recovery transient after GNSS returns) | 29.7 m |
| jamming | yes (C/N0, innovations, gate, unavailable) | 0 s | 0 | 15.0 m |
| **spoof_ramp** | **NO** | n/a | 10 (after the spoof stops) | **149.9 m** |
| spoof_step | yes, but only until the gate reset accepts the spoofed fix (41 of 150 epochs) | 0 s | 10 (after the spoof stops) | 121.3 m |
| inertial_drift | yes (heading residual, velocity innovation) | 197 s | 0 | 7.3 m |
| sensor_dropouts | yes, all three dropouts | 0 s | 0 | 2.7 m |

**What this shows, honestly:**

- The latch catches the loud, availability-type degradations at once (dropouts, jamming, missing sensors) and raises no alarm on the nominal run.
- It misses the slow, self-consistent spoof entirely while the spoof is active. The 0.5 m/s velocity offset stays below the declared 1.2 m/s velocity-innovation scale, and the constant-gain filter follows the ramp, so the position error grows to about 150 m.
- The abrupt spoof is caught only until the simple "re-initialise after 10 rejections" rule accepts it.
- Gyro drift is caught after about 3 minutes.

These are properties of these invented scenarios, the declared scales and this toy estimator. They say nothing about real systems.

In the 300 s dropout, dead-reckoning error at the end of the dropout is 29.5 m with the `classical_dr` profile (gyro bias 0.002 deg/s) and 2.2 m with the `hypothetical_low_drift` profile (0.00002 deg/s, a TARGET-style assumption). The difference follows directly from the assumed parameters. It is **not evidence about any real sensor**.

## Install and run

Python 3.10–3.13, standard library only. pilottrace is not a pip package, so it is used from a pinned checkout and hash-verified at runtime; a modified pilottrace is refused with exit code 3.

```bash
git clone https://github.com/sparkainlp-x/pilottrace .deps/pilottrace
git -C .deps/pilottrace checkout d402c09cfdd3282262efc3cecc290905623ad98d
python -m pilottrace_nav list
python -m pilottrace_nav run --out-dir replay-output        # all scenarios; or --scenarios nominal,jamming
python -m pilottrace_nav verify replay-output/provenance_manifest.json
python examples/navigation_replay.py                 # refreshes examples/output/
```

The per-scenario pilottrace traces and reports (about 3 MB each) go to `<out-dir>/traces/` and are not committed; the manifest records their hashes. **Exit codes:** `0` ok · `1` I/O error · `2` invalid arguments or fail-closed input · `3` pilottrace missing or not the pinned version · `4` verify mismatch.

## Tests

```bash
python -m pip install pytest pytest-cov
python -m pytest --cov        # 92 tests; coverage gate 95%
```

The tests cover:

- the formula worked by hand and the inclusive τ boundary;
- every fail-closed input path;
- the frame mapping order;
- agreement with `pilottrace.score_block`;
- determinism and shared noise across scenarios;
- the missing-sensor flags;
- refusal of a modified pilottrace;
- manifest tamper detection;
- CLI exit codes;
- byte-for-byte reproduction of the committed evidence.

CI runs ruff and the tests on Python 3.10–3.13, regenerates the evidence, and runs `cmp` against the committed copies.
